# Подключение серверных аккаунтов

Интерфейс остаётся на GitHub Pages. Supabase предоставляет авторизацию и PostgreSQL: общие полигоны, личную технику, зоны, глубины и траектории. До подключения действует прежний демонстрационный режим; он хранит свои старые данные только в браузере. Старые демо-аккаунты автоматически не переносятся в серверную авторизацию.

## Настройка проекта

Гараж поддерживает пользовательский ID (0–49). `create_equipment_with_id` создаёт технику с выбранным номером либо выбирает свободный автоматически; `set_equipment_marker` меняет ID только собственной техники. Проверка общих резерваций и блокировка строки полигона выполняются в одной транзакции, поэтому номера границ, зон и чужой техники нельзя занять повторно. Ошибка создания откатывает и технику, и её резервацию. Для действующей базы используйте обновлённый `transport-migration.sql`.

1. Создайте Free-проект в https://supabase.com/dashboard.
2. В **SQL Editor → New query** выполните весь `supabase/schema.sql`. Он создаёт таблицы, триггер регистрации, серверные операции и RLS. Повторное выполнение обновляет функции и политики, сохраняя данные таблиц. Если на сайте уже регистрировались пользователи до установки схемы, для них также создаются профили.
3. В **Authentication → URL Configuration** укажите Site URL `https://tfhguk.github.io/roi-site/`. Добавьте этот же адрес и `https://tfhguk.github.io/roi-site/login.html` в Redirect URLs.
4. В настройках API скопируйте **Project URL** и **Publishable key**. В GitHub-репозитории откройте **Settings → Secrets and variables → Actions → Variables**. Создайте переменные `SUPABASE_URL` и `SUPABASE_PUBLISHABLE_KEY`.
5. Запустите **Actions → Publish GitHub Pages → Run workflow**. Сборка подставит публичные параметры в `dist/cloud-config.js`. Для локальной разработки можно указать их в корневом `cloud-config.js`.
6. Проверьте регистрацию двух разных аккаунтов: второй видит первый полигон, но не видит технику, зоны, глубины и траектории первого пользователя.

Ключ `sb_publishable_…` или старый JWT с ролью `anon` предназначен для браузера. Сборка отклоняет Secret key и `service_role`. Ограничения доступа находятся в БД, а не в скрытии кнопок. Пароли обрабатывает Supabase Auth; приложение не сохраняет их в таблицах проекта.

Если в Supabase включено подтверждение email, после регистрации нужно открыть письмо и подтвердить адрес, затем войти. Для немедленного перехода после регистрации настройка подтверждения email должна быть выключена в **Authentication → Providers → Email**. Выбирайте режим проекта осознанно; код поддерживает оба варианта.

Официальные инструкции: [Auth](https://supabase.com/docs/guides/auth), [ключи API](https://supabase.com/docs/guides/getting-started/api-keys), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [тарифы](https://supabase.com/pricing).

## Этапы и сохранение

- Новый профиль получает `registration_status = polygon` — «Создание/выбор полигона».
- «Далее» после создания/выбора устанавливает `garage` — «Создание техники». Общая граница сохраняется сервером и доступна другим зарегистрированным пользователям.
- После добавления личной техники «Далее» устанавливает `zones`. Нужна минимум одна единица техники на выбранном полигоне.
- Нужны все четыре типа зон: `warehouse`, `charging`, `mining`, `transport`. После сохранения «Далее» устанавливает `routes`.
- Маршруты привязаны к личной технике. «Завершить настройку» устанавливает `ready`, только если серверная проверка всех траекторий проходит.

Каждая фигура редактируется вручную. Щелчок добавляет вершину, перетаскивание перемещает её, щелчок по ребру вставляет вершину. Выбранная вершина удаляется кнопкой или Delete. Ctrl+Z отменяет действия. Для зоны/траектории кнопка «Сохранить фигуру в проект» завершает редактирование черновика; «Сохранить на сервере» и «Далее» сохраняют весь проект в базе. При выходе с несохранёнными данными браузер предупреждает о них.

Полигон после публикации неизменен, чтобы редактирование одного пользователя не смещало рабочие зоны остальных. Для изменения выберите «Создать редактируемую копию». Переключение на другой полигон сбрасывает собственные зоны, глубины и траектории. Техника хранится с привязкой к полигону: при возврате на прежний полигон гараж снова показывает соответствующую технику.

Сервер резервирует `DICT_4X4_50` ID глобально в пределах полигона: граница, техника разных пользователей и вершины их зон не получают одинаковые метки. Всего доступно 50 ID на полигон. Граница ограничена 37 вершинами, чтобы оставалось место хотя бы для одной единицы техники и четырёх треугольных зон. Для нескольких пользователей и более подробных зон оставляйте больший запас ID. Перетаскивание вершины не меняет её ID, вставка получает новый. После сохранения обновите PDF перед физическим размещением новых меток. Экспорт PDF размещает две рукометки в ряд, шесть на страницу.

Рабочее поле нормировано в координатах 1000×700. По умолчанию показывается пустая сетка; переключатель включает камеру. Кадр можно зафиксировать. Фон камеры не передаётся в базу: сохраняется геометрия. Автоматического совмещения камеры с физической площадкой пока нет.

## Псевдокарта глубины

Формат JSON:

```json
{"version":1,"width":1000,"height":700,"cols":2,"rows":2,"unit":"условные единицы","cells":[0,1,null,2]}
```

Значения перечисляются по строкам сверху вниз. `null` означает препятствие, число от 0 до 1000 — глубину в условных единицах. Редактор принимает сетки от 2×2 до 100×100 и файлы до 2 МБ. Можно рисовать глубину кистью, отмечать препятствия, импортировать и скачивать JSON.

Если на этапе траекторий ещё нет путей и карта нулевая, автоматически создаётся синтетический рельеф 40×28 с плавными глубинами и случайными препятствиями. Существующая ненулевая карта используется без замены. Генератор работает в браузере; карта и пути сохраняются в серверной базе обычной кнопкой сохранения. В JSON сохраняются `source: "synthetic"` и `seed` для воспроизводимости (`SetupGeometry.generateDepth`). Кнопка «Сгенерировать тестовую карту и пути» создаёт новый случайный пример. Для серверной проверки транспортной области предусмотрена миграция ниже.

Транспортная зона — область разрешённого движения внутри полигона. Все остальные зоны должны находиться внутри неё; допускается объединение нескольких транспортных областей. Только самосвал перевозит грузы добыча ↔ склад и ездит на зарядку со склада. Бульдозер базируется на складе, погрузчик — в добыче; автоматически им создаются только выезды со своей базы на зарядку и обратно. Местные ручные перемещения в своей базе допускаются; отдельные искусственные рабочие поездки для погрузчика не создаются. Робот базируется на складе. Транспортная область не используется как цель. У маршрутов сохраняются `purpose` (`haul`, `charging`, `manual`) и `bidirectional`; путь можно проходить туда и обратно.

При завершении настройки сервер проверяет назначение техники и расположение концов маршрута. Для погрузчика допустимы концы в добыче или зарядке, для бульдозера и робота — в складе или зарядке; перевозки с `purpose=haul` для них запрещены. Полные отрезки проверяются относительно транспортной области, глубины, препятствий и отступов. Обновлённый [transport-migration.sql](transport-migration.sql) переводит сохранённый тип `excavator` в `bulldozer`, сохраняет ID/ArUco и пользовательские названия и добавляет совместимость старого значения при вызове `create_equipment`. Повторное выполнение допустимо; миграция не удаляет технику и маршруты. Несовместимые старые маршруты нужно перестроить.

Поиск сначала минимизирует наибольший перепад между ячейками, затем суммарное изменение глубины, затем длину. Используются два прохода по графу: поиск минимального допустимого перепада и поиск пути с этим пределом. Кроме центров ячеек учитываются видимые вершины разрешённой области, чтобы проходить узкие изогнутые коридоры. Прямой допустимый отрезок не имеет приоритета перед пологим обходом. При упрощении нельзя увеличить найденный предельный или суммарный перепад. Ограничения максимальной глубины и перепада остаются обязательными.

Генератор seed сохраняет непрерывную сеть свободных проходов между рабочими зонами до размещения случайных препятствий. Рельеф ограничивается выбранными глубиной и перепадом, включая нулевой перепад. Если транспортные области разъединены или рабочая зона находится снаружи, генерация сообщает об ошибке и сохраняет предыдущий проект. Импортированные карты не изменяются ради проходимости: для непроходимой карты выводится ошибка. Это набор допустимых соединений, а не расписание движения; габариты, радиус поворота и столкновения нескольких машин пока не моделируются.

Повторное автопостроение запрашивает подтверждение замены ручных правок. Можно выбрать всю технику или одну машину; во втором случае пути остальных машин сохраняются. Максимум 30 траекторий на проект. Изменение глубин вручную или импорт JSON не стирает правки маршрутов: они проходят повторную проверку, после чего можно перестроить их кнопкой «Построить автоматически» либо отредактировать вручную.

У каждой траектории сохраняются `number`, `boundaryClearance` и `markerClearance`; поле `number` остаётся для совместимости сохранённых проектов. Интерфейс группирует маршруты под именами техники. Наведение на карточку показывает точки её путей, нажатие закрепляет выбор; кнопки «Изменить» и «Удалить» находятся рядом с именем маршрута внутри карточки. Номера маршрутов и подписи поворотных точек на карте не показываются. ArUco ID техники виден в карточке, рукомаркеры границ и зон сохраняют свои подписи.

Отступ от границы по умолчанию 5, от центра рукомаркера — 40 единиц карты. Расстояние проверяется для каждого полного отрезка, включая его середину, а также при упрощении найденного пути. Учитываются метки вершин общего полигона и собственных зон. Внутренние швы пересекающихся транспортных областей не считаются границей дороги. Дополнительные точки поиска позволяют обходить метки, не приближаясь к ним. Узкие проезды не открываются уменьшением выбранных отступов. Если места не хватает, расширьте площадку или задайте обоснованные размеры техники и запаса. Нельзя завершить настройку с отступом от границы меньше 1 или от центра метки меньше 24. Обновлённый `transport-migration.sql` включает серверную проверку этих условий и применяется без удаления данных.

У каждой траектории задаются максимальная глубина и максимальный перепад между соседними пересечёнными ячейками. Проверка учитывает полные отрезки, вогнутые границы и касание препятствия на границе ячейки. Недопустимый маршрут можно сохранить как черновик и исправить; завершение настройки блокируется и в интерфейсе, и сервером. После изменения карты или геометрии завершённый профиль возвращается на проверку траекторий. Проверяется центральная линия; габариты техники и реальная метрическая калибровка пока не моделируются.

Сохранение использует номер `revision`, чтобы вкладки не перезаписывали чужие более новые изменения без предупреждения.

## Проверки

```powershell
npm.cmd install
npm.cmd run build
npm.cmd run test:setup
npm.cmd run test:pages
```

`test:setup` запускает настоящую PostgreSQL-схему в PGlite, проверяет RLS, серверные статусы, выделение ID и валидацию маршрутов. Два браузерных контекста проходят регистрацию и работу с общим полигоном. Только HTTP-слой Supabase Auth заменён тестовым адаптером на localhost; реальный проект Supabase подключается публичными параметрами, описанными выше. Тесты не создают пользователей в вашем облачном проекте.
